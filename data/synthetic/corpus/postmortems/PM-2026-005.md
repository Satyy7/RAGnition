# PM-2026-005: Orders stuck - order-worker in CrashLoopBackOff  
**Date:** 2026-04-29 **Severity:** SEV2 **Service:** order-worker  

## Summary  
During a Spring promotion, the `order-worker` service entered a CrashLoopBackOff state after its pods were OOMKilled. The incident lasted 75 minutes, delaying roughly 2,100 orders from reaching the warehouse.

## Impact  
- Approximately 2,100 orders were delayed.  
- Delay per order: up to 75 minutes.  
- No data loss; orders were processed once the service recovered.

## Detection  
The `OrderHandoffDelay` alert fired at 10:12 UTC, indicating that orders were not being handed off to the warehouse within the expected SLA.

## Timeline  
- **10:00** – Spring promotion with gift messages and large multi‑item orders begins.  
- **10:12** – `OrderHandoffDelay` alert triggers.  
- **10:20** – `kubectl describe` on the `order-worker` pods shows `Last State: Terminated, Reason: OOMKilled` (exit code 137). Pods enter CrashLoopBackOff.  
- **11:15** – Memory limit increased to 1 Gi (CHG-2240) and new configuration rolled out. Pods restart successfully.  

## Root cause  
Building fulfilment documents for the unusually large orders consumed ~700 MiB of memory, exceeding the pod’s configured limit of 512 MiB. The OOMKill caused the containers to exit with code 137 and enter CrashLoopBackOff.

## Trigger  
The promotion introduced gift messages and large multi‑item orders, which increased the size of fulfilment documents and consequently memory usage.

## Resolution  
Memory limit for the `order-worker` pods was raised from 512 MiB to 1 Gi (CHG-2240). The updated limit provided sufficient headroom for peak memory consumption, allowing the pods to restart and process the backlog.

## Contributing factors  
- Memory limits were derived from average usage rather than peak usage.  
- No additional headroom was built into the limits to accommodate traffic spikes.

## Action items  
- Size memory limits from the p99 peak usage plus a 30 % safety margin, never from averages (completed; documented in the platform handbook).  

## Lessons learned  
- **Peak‑based sizing:** Resource limits must be based on observed peak consumption, not on average metrics, to prevent OOM events during traffic spikes.  
- **Headroom policy:** Adding a defined safety margin (e.g., 30 %) to peak usage helps absorb unexpected load surges.  
- **Alert correlation:** Early detection via SLA‑based alerts (e.g., `OrderHandoffDelay`) is valuable, but coupling alerts with resource‑usage monitoring can surface OOM risk sooner.  
- **Promotion readiness:** New promotional features should be load‑tested with realistic order sizes to verify that resource limits remain adequate.
