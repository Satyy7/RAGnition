# PM-2025-011: Search cluster yellow, new products missing from search  
**Date:** 2025-06-02 **Severity:** SEV2 **Service:** search-api  

## Summary  
A reindex operation created a duplicate `products-*` index, pushing two OpenSearch data nodes over the 90 % high‑disk watermark. The nodes stopped allocating shards, leaving replicas of new indices unassigned and causing indexing to stall. Search remained available, but new and updated products were absent from results for ~3 hours.

## Impact  
- New and updated product records were not searchable for approximately 190 minutes.  
- Existing search functionality stayed up; users could query but would not see recent catalog changes.

## Detection  
The `SearchIndexLag` alert fired at 10:48, 40 minutes after the reindex job began, indicating that indexing was falling behind expected rates.

## Timeline  
- **10:05** – Reindex job for `products-*` started.  
- **10:48** – `SearchIndexLag` alert triggered.  
- **11:30** – `_cluster/allocation/explain` showed that the high‑disk watermark (90 %) had been exceeded on two data nodes.  
- **13:15** – Old duplicate index deleted after alias switch; shards began allocating and indexing resumed.  

## Root cause  
The temporary duplicate index generated by the reindex consumed enough disk space to push two data nodes past the 90 % high‑disk watermark. OpenSearch’s allocation decider stopped assigning shards to those nodes, leaving replicas of the new indices unassigned and halting indexing.

## Trigger  
The reindex operation itself created a full second copy of the `products-*` index, which doubled the disk usage on the affected nodes.

## Resolution  
Deleted the old duplicate index after switching the alias to the new index. Disk usage fell back to 61 %, allowing shard allocation to proceed and indexing to recover.

## Contributing factors  
- No alert existed for disk usage crossing the high‑watermark threshold, so the situation was not detected until indexing lag manifested.

## Action items  
- **Alert on data node disk above 80 %** – implemented.  
- **Reindex runbook update** – added a pre‑check to verify that free disk is at least twice the size of the index to be created – implemented.

## Lessons learned  
- Disk capacity planning must consider temporary storage needs during large reindex operations; a single reindex can temporarily double index size on a node.  
- Monitoring should include alerts for both low‑watermark and high‑watermark thresholds to catch disk pressure before allocation stops.  
- Runbooks for disruptive operations (e.g., reindex) should enforce pre‑flight checks on resource availability to prevent inadvertent cluster health degradation.
