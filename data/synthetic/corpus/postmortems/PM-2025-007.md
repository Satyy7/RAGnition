# PM-2025-007: Payment authorizations failing during spring sale  
**Date:** 2025-03-14 **Severity:** SEV1 **Service:** payments‑api  

## Summary  
During the peak of the spring sale, payment authorizations experienced a 503 error rate of ~18% for 47 minutes. The incident was triggered by a mismatch between the scaled number of application replicas and the default connection pool size in PgBouncer, causing connection starvation and request timeouts.

## Impact  
- Approximately 18 % of payment authorization attempts failed with HTTP 503.  
- Failures occurred during the highest traffic period of the sale, affecting revenue and customer experience.  
- The issue persisted for 47 minutes before remediation.

## Detection  
- At 19:02, the **PaymentsErrorRateHigh** alert fired, indicating an abnormal rise in error rate.  
- Customers began reporting failed payments shortly thereafter.

## Timeline  
- **19:00** – Sale traffic ramps up.  
- **19:02** – PaymentsErrorRateHigh alert fires.  
- **19:15** – Application logs show “timeout acquiring connection from pool”.  
- **19:31** – PgBouncer `SHOW POOLS` reports `cl_waiting` = 160.  
- **19:49** – Replicas reduced from 12 to 8; errors begin to recover.  

## Root cause  
The spring‑sale scaling increased payments‑api to 12 replicas, generating up to 240 concurrent client connections. PgBouncer’s default pool size was still set to 30 server connections, far below the required capacity. Requests queued in PgBouncer (`cl_waiting` > 150) timed out after 5 seconds in payments‑api, resulting in HTTP 503 responses.

## Trigger  
The scaling change **CHG-2101** doubled the number of application replicas without adjusting PgBouncer’s connection pool configuration, creating a demand that exceeded the pooler’s capacity.

## Resolution  
- PgBouncer `default_pool_size` was increased from 30 to 60.  
- Application replicas were reduced from 12 to 8, aligning client connection demand with the enlarged pool size.  

## Contributing factors  
- No alert existed for PgBouncer `cl_waiting` metric, so the connection‑pool saturation was not surfaced early.  
- Capacity planning accounted for replica count but omitted the corresponding pooler sizing, leading to an under‑provisioned PgBouncer configuration.

## Action items  
- Implement an alert when PgBouncer `cl_waiting` > 0 for 2 minutes (completed).  
- Add a capacity rule that **replicas × app pool size** must fit within `default_pool_size` plus headroom (completed, documented in runbook).  

## Lessons learned  
- Scaling an application horizontally must be accompanied by proportional scaling of shared resources such as connection poolers.  
- Monitoring of critical pooler metrics (e.g., `cl_waiting`) is essential to detect saturation before it impacts downstream services.  
- Capacity planning documentation should explicitly tie replica counts to connection‑pool limits to prevent similar mismatches in future events.
